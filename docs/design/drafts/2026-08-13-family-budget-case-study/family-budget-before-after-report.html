01 · System boundary

같은 화면, 다른 데이터 경계

텍스트 설명

보이는 React 컴포넌트는 공개 패키지에서 동일하게 소비합니다. 차이는 runtime contract 뒤의 read/command adapter뿐입니다.

공개 경로: 추적된 합성 seed를 읽고 브라우저 localStorage에만 변경을 저장합니다.

비공개 경로: 인증된 API와 운영 저장소를 유지합니다. 상세 URL·DB·자격증명·실데이터는 공개 근거에서 제외합니다.

02 · Why / How / Result

세 가지 문제 해결 이야기

Story 1

복제 UI가 다시 어긋나지 않게

Why: 데모 복제본은 운영 UI가 변할 때 즉시 낡았습니다.

How: canonical source를 공개 package로 추출하고 exact/seam 파일을 SHA manifest로 구분했습니다.

Result: 소비자는 package export만 사용하며 원본 우회 alias를 검사로 차단합니다.

Story 2

화면 정합성과 데이터 격리를 동시에

Why: 동일 화면을 원하면 private API 의존도 함께 끌려올 위험이 있었습니다.

How: read provider와 command adapter를 runtime seam으로 분리했습니다.

Result: 확인된 synthetic read path가 fetch를 호출하지 않는 테스트와 정해진 literal 범위의 public-boundary scan을 유지합니다.

Story 3

빌드 성공을 화면 품질로 오해하지 않게

Why: 표 기반 화면 4곳의 overflow가 독립 브라우저 QA에서 발견됐습니다.

How: canonical component의 responsive CSS와 44px target·focus gate를 수정했습니다.

Result: 7 routes × 3 viewport document overflow 0 후에만 release했습니다.

03 · Decisions

선택과 대가

공개 package + 고정 SHA

선택: 소스 복사나 private source alias 대신 명시적 package export를 사용.

이유: 정합성과 공개 경계를 자동 검증할 수 있음.

대가: 공개 package release와 private consumer pin을 함께 관리해야 함.

Mock API 대신 browser adapter

선택: 별도 공개 backend 없이 synthetic seed와 localStorage 사용.

이유: 자격증명·운영 DB 없이 read/write 흐름을 직접 체험 가능.

대가: 다중 사용자·서버 동기화·복구를 증명하지 않으며 이를 한계로 명시.

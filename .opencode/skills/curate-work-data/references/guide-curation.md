# guide-curation

work-data를 이력서 문장으로 전환할 때는 "많이 쓰는 것"보다 "잘 고르는 것"이 중요하다.
이 가이드는 월간 큐레이션에서 문장 품질을 안정적으로 유지하기 위한 기준을 제공한다.

## 1) 작성 철학

### 시니어 문장 원칙: 문제-해결-결과 덩어리형

- 시니어 레벨 문장은 배경 설명보다 의사결정과 효과를 빠르게 전달해야 한다.
- 한 문장 안에서 `문제 → 해결 → 결과`가 자연스럽게 이어지면 읽는 사람이 맥락을 바로 잡는다.
- 장황한 서론 대신, 영향과 책임 범위를 먼저 드러내는 편이 HR 스캔 효율이 높다.

예시 (좋음):

- 결제 정산 배치 병목으로 인한 지연 문제를 큐 구조 재설계와 병렬 처리로 해소하여 정산 완료 시간을 42% 단축

예시 (아쉬움):

- 결제 시스템을 개선했고 다양한 최적화를 진행하여 전체적으로 더 좋아짐

## 2) 프로젝트 하이라이트 한 줄 공식

프로젝트 하이라이트는 아래 순서를 기본으로 사용한다.

`도메인 + 문제 + 해결 + 결과`

이 순서는 "무슨 영역인지"를 먼저 고정하고, 왜 중요한 일을 했는지 빠르게 설명한다.

### 템플릿

- `[도메인] [문제]를 [해결 방식]으로 개선하여 [결과] 달성`

### 예시

- AI QA 자동화 도메인에서 회귀 검증 누락 문제를 멀티에이전트 시나리오 오케스트레이션으로 보완하여 리뷰 리드타임 35% 단축
- 대용량 정산 도메인에서 재처리 실패율 증가 문제를 재시도 정책과 idempotency key 도입으로 해결하여 장애 재발률 감소

## 3) 기본기 60% + 강점 40%

"당연히 알 거라고" 생략하면 오히려 약하게 보인다.

- 기본기 60%: 운영 안정성, API 품질, 테스트/검증, 데이터 일관성
- 강점 40%: AI Native orchestration, 성능 최적화, 자동화/생산성 향상

프로젝트 단위로 보면, 최소 절반 이상은 기본기 기반 성과를 포함시키는 편이 신뢰도를 높인다.

## 4) 단순 구현도 이유를 붙여라

구현 자체보다 "왜 이 선택이 유효했는지"가 평가 포인트다.

- 아쉬운 문장: 캐시를 적용함
- 개선 문장: 반복 조회로 인한 응답 지연을 줄이기 위해 캐시 계층을 적용해 P95 응답시간 안정화

## 5) KO/EN 문체 규칙

### KO: 명사형 종결 유지

명사형은 이력서 톤을 일정하게 유지하고 불필요한 감정 표현을 줄여 준다.

좋은 패턴:

- 구축
- 개선
- 정착
- 최적화
- 자동화
- 고도화

아쉬운 패턴:

- 했습니다
- 만들었습니다
- 진행했습니다

### EN: Past-tense Action Verb

영문은 동사로 시작하면 책임과 행동이 선명해진다.

추천 동사:

- Designed
- Implemented
- Reduced
- Improved
- Stabilized
- Automated

피하고 싶은 시작:

- Was responsible for
- Worked on
- Helped with

## 6) STAR 구조 적용법

하이라이트를 작성할 때 STAR를 완전한 4문장으로 늘어놓기보다, 한 줄 안에 압축한다.

- Situation/Task: 어떤 문제였는가
- Action: 무엇을 어떻게 바꿨는가
- Result: 어떤 결과가 검증되었는가

압축 예시:

- 배치 실패 누적으로 마감 지연이 발생하던 상황에서 재시도 정책과 알림 자동화를 도입해 월말 수작업 복구를 제거

## 7) work-data → resume 매핑 규칙

`resumeProject`는 큐레이션의 기본 연결 키다.

1. `resumeProject` 값이 있는 항목은 해당 프로젝트로 우선 배정
2. `resumeProject == null`이면 도메인/태그/outcome을 근거로 후보 프로젝트를 제안
3. 동일 프로젝트 내 유사 토픽은 중복 제거 후 하나의 강한 문장으로 병합
4. 같은 성과를 ko/en에서 서로 다르게 해석하지 않도록 의미 동기화

## 8) AI 슬롭 금지어

문장이 번듯해 보여도 채용 문서에서는 신뢰를 떨어뜨릴 수 있다. 아래 표현은 사용하지 않는다.

### KO 금지어/패턴

- 혁신적
- 획기적
- ~를 통해
- 함으로써
- 뿐만 아니라
- 나아가

### EN 금지어

- leveraging
- comprehensive
- robust
- streamline
- cutting-edge
- utilize
- foster
- delve
- seamless
- groundbreaking
- transformative

## 9) 과장 방지

- work-data에 없는 수치는 만들지 않는다.
- "업계 최고", "세계적", "완전한" 같은 절대 표현은 근거 없으면 제거한다.
- 정량이 없을 때는 정성 효과를 과장하지 말고 맥락 중심으로 쓴다.

## 10) 7.4초 가독성 체크

리크루터 스캔 기준으로 다음을 확인한다.

1. 한 문장에서 핵심 메시지 1개가 즉시 읽히는가
2. 기술 키워드가 묻히지 않는가
3. 문장이 길어도 구조가 단순한가

긴 문장은 접속사를 늘리기보다 문장 자체를 재배열해서 짧게 만든다.

### 100자 초과 문장 압축 기법

details가 100자를 넘으면 PDF에서 줄바꿈이 잦아지고 스캔 가독성이 떨어진다.
아래 기법을 순서대로 적용해 100자 이내로 압축한다.

**기법 1: 중복 구조어 제거**
- Before: "ORM 단건 저장을 벌크 연산으로 전환하여 Image 동기화 시간을 72% 단축(25.7s→7.1s)하고, DB 트랜잭션을 95% 감소(10~16s→0.3~0.5s)시킴"
- After: "ORM→벌크 전환으로 동기화 72% 단축(25.7s→7.1s), 트랜잭션 95% 감소"
- 원리: "전환하여", "시킴" 같은 연결어를 제거하고 콤마로 병렬

**기법 2: 도메인 접두사 분리**
- Before: "glider-sheet 업그레이드 자동화: GitHub Packages 기반 배포 파이프라인 위에 GitHub Actions workflow_dispatch와 matrix 병렬 실행으로 7개 프로젝트 일괄 업그레이드 자동화(수동 약 3시간→15분)"
- After: "업그레이드 자동화: workflow_dispatch + matrix 병렬로 7개 프로젝트 일괄 처리(3시간→15분), GitHub Packages 배포"
- 원리: 프로젝트명(glider-sheet)은 상위에서 이미 보이므로 제거. 기술 스택은 최소 키워드만

**기법 3: 결과를 괄호로 압축**
- Before: "CI 평균 시간을 15분47초에서 6분06초로 61% 단축하고 전체 81 suites 978 tests 통과를 확인"
- After: "CI 61% 단축(15m47s→6m06s), 81 suites 978 tests 통과"
- 원리: before→after는 괄호 안에, 서술어 제거

**기법 4: 판단 근거를 분리**
- 100자가 넘는 이유가 "판단 근거 + 실행 + 결과"를 한 문장에 넣어서인 경우:
- 판단 근거는 별도 bullet으로 분리하거나, 짧은 부사절("~보다 ~를 우선하여")로 축약

**적용 순서**: 기법 1→2→3 순으로 시도. 그래도 100자 초과면 기법 4로 문장 분리.
**제한**: 압축 시 핵심 수치와 기술 키워드는 반드시 보존. 수치를 삭제해서 줄이는 것은 금지.

## 11) 부정 인식 회피

약점처럼 읽힐 여지가 있는 표현은 관점 전환으로 바꾼다.

- 아쉬움: 코드를 거의 안 치고 조율만 진행
- 개선: 아키텍처 설계와 검증 자동화에 집중해 팀 구현 품질과 릴리즈 안정성 확보

## 12) ATS 키워드 보존

문장을 다듬더라도 핵심 기술 키워드는 지운다기보다 자연스럽게 재배치한다.

보존 우선 키워드 예시:

- Backend
- TypeScript
- AWS
- NestJS
- PostgreSQL
- CI/CD
- Observability

## 13) 최종 점검 루틴

반영 전 최소 점검 순서:

1. 팩트 일치 (work-data 근거)
2. 문체 일관성 (KO 명사형 / EN 과거형)
3. 금지어 0건
4. 과장 0건
5. 7.4초 가독성
6. 부정 인식 없음
7. ATS 키워드 보존

이 루틴이 통과되면, "자연스럽고 검증 가능하며 채용 친화적인" 문장에 가까워진다.
